## 概述

这场 YC Startup School 对话把 Jeff Dean 的系统观压缩成一条完整链路：模型能力先从更长的 agent 执行时间外溢，再被推理延迟和能耗约束；真正可用的 agent 则需要把人类的工作方法写成 skills，并用多路径搜索和 evaluator 对抗分布外漂移。它最终导向的不是“人人都有一个万能 agent”，而是更具体的判断：通用模型越强，创业团队越应围绕私有数据、极窄问题和明确验收标准构建系统。

## 主题脉络

1. Agent 的任务周期会从小时延伸至数日乃至数周，但可靠性不是自然获得的。
2. 推理的竞争对象不是训练吞吐，而是数据移动、能耗和交互延迟。
3. Context engineering 的实质是把任务知识、工具和评估循环显式放进模型可见上下文。
4. 小团队的机会不在复刻通用模型，而在获得通用模型没有的数据和可度量的窄任务。
5. 自动化科学方法的瓶颈不是生成更多方案，而是把 evaluator 的速度提升到足以支撑实验闭环。

## Agent 跑得更久，不代表它会自己变可靠

Dean 先把一个尚未被市场充分内化的能力边界讲得很明确：在合适问题域与足够强的底层模型上，agent 已可运行“days or weeks”并完成复杂任务 [4:51-5:20]。他给的例子不是泛化的办公助手，而是让 agent 重写软件实现，以换取安全性或性能属性 [5:28]。这说明“长运行”首先适合目标、产物和验收都相对清楚的工程任务。

但他紧接着解释了为什么今天的 agent 往往在十几次工具调用后失稳：一旦任务偏离模型训练经验的分布，性能会突然下降，且偏离越远越不可靠 [22:41-23:07]。因此，他提出的修复路径不是更长的 prompt，而是三件可操作的系统能力：

- 用 skills 和 hints 把模型留在它熟悉的“brightly lit path” [23:30]；
- 让多个 agent 尝试不同路径，再由另一模型或 agent 评估有希望的分支 [23:30-23:58]；
- 将这一过程理解为 inference-time compute 上的路径搜索，而非单次生成 [23:58]。

这里的隐含立场很重要：Dean 没有把长运行 agent 描述为“模型终于足够聪明”，而是把它当成一个被 harness 约束的搜索过程。模型是其中一层；skill、candidate generation、evaluator 和淘汰机制共同决定系统能否走过第 50 步。对做 agent 产品的团队而言，应该按任务轨迹的失败点来建设 skill 和验证器，而不是只比较基础模型首轮回答。

## 推理硬件的关键指标是延迟和数据移动

Dean 认为，agent 能否普及并不只取决于模型能力。围绕推理，他判断更高性能、低能耗的专用硬件会越来越重要，因为推理是让 agent 系统触及更多用户的关键，而低延迟决定其是否能成为交互基础设施 [3:36-4:01]。他用“50x better”延迟的设想追问产品形态会如何变化 [4:30]，但没有给出确定的产品结论，重点仍在系统约束本身。

他的能耗解释比“算力不够”更具体：从加速器的高带宽内存把数据搬进处理器，其能耗可能比一次计算高约千倍；这迫使训练用 batch 来摊薄数据移动成本，而极低延迟场景却并不适合 batching [12:33-13:36]。于是，训练最优和交互推理最优会分叉。Dean 对推理专用化的兴趣集中在减少数据移动、极低精度运算，以及在已知精度需求后删除不必要的硬件通用性 [14:43-15:07]。

产业信号不是“TPU 将替代所有 GPU”。Dean 自己把 TPU 的原始选择解释为：既要足够通用以适应仍在演化的 ML 算法，也要足够专用以获得大幅性能收益 [8:40-9:09]。这是一条面向工作负载稳定性的设计原则：当模型形状和推理路径尚未稳定时，过度专用化会锁死未来；当延迟、精度和数据流足够确定时，专用化才开始释放决定性的成本和速度优势。

## Context engineering 是把人的工作法变成模型可执行的环境

Dean 对 context engineering 的定义很少谈 prompt 技巧。他说模型只是整体系统的一部分；系统还需知道如何调用工具、检索哪些信息、保留过去检索结果，并把与当前任务相关的信息直接放进上下文 [16:42-17:11]。这比把知识留在参数中更可控，因为当前上下文对模型是清晰、可定位的。

他随后把复杂 agent 的核心落到工具选择、问题分解、多方案尝试和结果评估 [17:36-18:02]。实际例子是他与 Sanjay 为低层库性能优化写出的 skill：该 skill 指导模型按“测量基线、修改代码、重新测量、扩大 benchmark”循环工作 [20:28-21:14]。这里没有声称模型拥有 Jeff Dean 的通用判断力，恰恰相反，原话是：

> **[21:14]** "And it really just is us giving the approach we would use as people to the model in a form that it could use."

这句话把所谓 agentic workflow 的价值边界说透了。可复制的不是专家身份，而是专家在一个任务类上已经验证过的观察顺序、工具使用方式和验收信号。对组织而言，最有价值的内部资产会从“给模型一个好问题”转向把反复有效的工作方法沉淀为可调用 skill，并持续用失败案例修订它。

## 小团队的窗口在私有上下文和 0% 成功率问题

面对“Google 从模型到芯片都在联合构建，小团队还能在哪赢”的问题，Dean 的回答很克制：通用模型为了覆盖几乎所有事情，不会对每个领域投入足够注意力；小团队可以用设计得很好的产品界面、skills，或特定模型，在自己极其了解的领域提供高准确率和高质量体验 [25:57-26:19]。

但他也给出筛选标准，避免把“垂直”误解为天然护城河。若通用模型已经能做一部分，只是做得不够好，这通常意味着能力已出现，未来六到十二个月很可能继续改善；应寻找通用模型目前只做到 0% 或 1%、而非 20% 的问题 [26:50-28:28]。他给出的两类结构性优势是：产品能看到通用模型没有的用户私有信息，或用合适数据训练一个成本可承受、但精度很高的专用模型 [29:04-29:31]。

这段的行业信号是，创业机会从“把通用模型包成某行业聊天框”转向两种更难复制的资源：数据可见性，以及可重复验证的窄任务。Dean 的隐含立场也很明确，他并未否认通用模型会吞掉大量产品表层，反而要求创始人在下注前直接测试前沿模型，并把能力曲线纳入产品的存续判断。

## 自动实验闭环的上限由 evaluator 决定

Dean 对“AI 构建更好的 AI”的表述仍然以科学方法为中心：提出实验、实施实验、评估结果，然后依据结果再迭代 [42:32-42:58]。自动化带来的增量不只是实验数量，而是把循环延迟压低，使高层目标能被分解为多个自动探索子问题，再合成为整体解 [43:23-43:50]。

他的关键限制条件出现在对可验证性问题的回应中：有些领域的 evaluator 本身需要更快 [44:15]。量子化学的例子展示了这一点，团队用昂贵模拟器的输入输出训练近似验证模型，把单次约一夜的计算压缩到快 300,000 倍、且接近原有精度 [44:28-45:46]。因此，自动实验真正改变速度的前提不是生成更多候选，而是将验证器加速到候选空间可以被高频筛选的程度。

这给产业判断划了一条清晰边界：拥有“自动跑实验”的 agent 并不等于拥有自我改进系统。只有目标可拆解、候选能被廉价评估、结果能回流下一轮决策的场景，实验自动化才形成复利。没有快速 evaluator 的领域，更多 agent 只会提高探索成本和结果噪音。

## 关键判断

- 长运行 agent 的可靠性是 harness 产物：skills 限制分布外漂移，多路径搜索扩展候选空间，evaluator 决定哪些轨迹保留 [23:07-23:58]。
- 推理基础设施的核心约束正由训练吞吐转向延迟、数据移动与能耗；能耗结构将反过来塑造 batching、精度和芯片专用化 [12:33-15:07]。
- Context engineering 的关键产物不是更长上下文，而是可观察、可执行、可评估的任务环境 [16:42-21:14]。
- 小团队应避开通用模型已达到 20% 的能力前沿，优先寻找模型仍是 0% 或 1%、且自己拥有私有数据或专业评估条件的问题 [26:50-29:31]。
- AI 加速科学与工程的最大杠杆是验证环节速度，而不是方案生成数量 [42:32-45:46]。

## 深度关联
> 以下关联基于论点级分析：不是「都提到了X」，而是具体论点之间的逻辑关系

### 长运行 agent 把 Brown 的预算轴落到具体系统结构
**← [[Noam Brown- Test-Time Compute Changes Benchmarks, Safety and Research]]**
- 本文件论点：Dean 将长运行可靠性拆成 skills、候选路径搜索和 evaluator，并明确把多路径探索称为 inference-time compute [23:30-23:58]。
- 对方论点：Brown 认为模型能力是模型、预算、运行时间与 scaffold 的函数，固定单分数 benchmark 会遗漏高预算能力 [0:00, 3:31]。
- 关联逻辑：Brown 提出“能力随预算变化”的测量问题；Dean 给出预算在工程系统中实际花到哪里：不是单纯延长思考，而是让多个候选路径接受筛选。两者合起来意味着 agent 评估必须记录 scaffold、分支数、evaluator 与运行时预算，否则只是在比较不等价的系统。

### 低延迟推理是跨层协同设计的具体工作负载
**← [[Dylan Patel- Why Hardware-Software Co-Design Is AIs Real 100x]]**
- 本文件论点：Dean 将低延迟推理的瓶颈定位为数据移动和能耗，指出极低延迟与大 batch 的效率逻辑相冲突 [12:33-15:07]。
- 对方论点：Patel 认为模型形状、kernel、网络拓扑、硅片和数据中心必须共同优化，单层改进无法解释 AI 的效率曲线。
- 关联逻辑：Patel 提供跨层联合设计的行业框架，Dean 则把它缩小为一个可计算的设计张力：数据移动能耗要求 batching，交互推理又要求不 batching。专用推理硬件的价值取决于能否在该张力下重新设计模型、内存和系统路径，而不是抽象地“更快”。

### 多 agent 不是人数扩张，而是带验证器的搜索架构
**← [[Diamandis #231- 多 Agent Scaling、OpenClaw 与权限边界]]**
- 本文件论点：Dean 主张多个 agent 尝试不同方法，并由 evaluator 选择有希望路径、丢弃失控路径 [23:30-23:58]。
- 对方论点：Diamandis #231 将 multi-agent teaming 视为新的 scaling 维度，并指出上下文共享、工具权限和结果合并决定真实能力。
- 关联逻辑：前者补上了后者容易被忽略的技术条件：并行 agent 只有在能评估并淘汰分支时才提升可靠性，否则只是更昂贵的并发。结合 OpenClaw 的常驻权限风险，agent team 的产品竞争不应只比并发数，还要比评估、审计与停止机制。

### 自动化实验把“模型改进模型”从叙事改写为验证吞吐问题
**→ [[Yann Dubois- Why AI Progress Suddenly Feels Real]]**
- 本文件论点：Dean 认为自动化实验循环的关键是将 evaluator 加速，使候选可以被高频筛选；量子化学近似验证器将一次验证从一夜压缩至接近 300,000 倍更快 [44:15-45:46]。
- 对方论点：Yann Dubois 指出 agent RL 在长 rollout 中存在信用分配稀疏性，最终很难知道哪一步导致正确 [41:23]。
- 关联逻辑：Dubois 说明长轨迹学习缺少有效反馈，Dean 给出一种更工程化的缓解方向：更快、更便宜的 evaluator 让反馈密度提高。它不能自动解决所有信用分配问题，但把“自我改进”从模型人格化叙事还原为实验、评估和反馈吞吐的系统工程。
