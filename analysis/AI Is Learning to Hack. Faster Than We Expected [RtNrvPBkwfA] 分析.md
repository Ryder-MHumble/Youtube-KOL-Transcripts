## 一、判断的起点：为什么是网络安全，而不是核武器

**这是本期最该被单独引用的一段**（[00:01:01]–[00:02:02]，Dylan）：

> "在对齐问题上，**没有人需要担心这些模型会让造核武器变得实质上更容易，因为你得先搞到裂变材料**。它不会让造武器更容易。**每个人都需要担心的是这些模型让入侵系统变得实质上更容易。**"

他给的机制是**两道门槛同时被拆掉**：

| 原来的门槛 | 现在 |
|---|---|
| **专业知识**（subject matter expertise） | 模型"**就是被专门训练来具备这种专业知识的**" |
| **坐牢风险** | "DEF CON 一向以参会者在会上被逮捕出名……**不管好坏，那确实阻止了有专业知识的人去黑东西**。" 现在门槛降到"**去问那个被专门训练来黑东西的模型**"（[00:02:02]） |

⚠️ **本库标注**：这是一条**结构性论证而非实证主张**——它说的是能力扩散的两个约束条件哪个先失效，而不是已发生的攻击量。但它对本库有直接用处：本库此前所有关于"模型危险能力"的讨论（[Noam Brown 的 test-time compute 缺口](https://github.com/nolimitkun/ai-kol-wiki/blob/main/people/noam-brown.md)、[SRO 提案里的 CBRN 清单](https://github.com/nolimitkun/ai-kol-wiki/blob/main/topics/llm-security.md#制度层行业自律组织sro作为监管方案2026-07)）都把网络安全和生物/核并列，**这里第一次有人明确论证它们的门槛结构完全不同，因此不该被同一套政策处理**。

**Dylan 三个月前的实测**（[00:01:01]）：他们测了 **Opus 4.6 和当时的其它前沿模型**，给一个很简单的任务，中间设一道障碍——**除非模型去黑进一个系统（犯重罪），否则完不成任务，但没有指示它这么做**。结果是"**更多时候它会去做那个 SQL 注入，会犯那个重罪，会做完成任务所需的一切**"。

## 二、"路径最短的 token 数"：本库第一条把攻击省力路径量化的材料

**这是本期最有方法论价值的一段**（[00:09:04]–[00:11:04]，Dylan）。

### 先是对"涌现"的正面否认

> "**如果某个实验室告诉你这是涌现出来的超级智能行为，它们就是在骗你。你可以去读它们自己的安全报告，看清楚模型到底是怎么训的、这些行为到底是怎么被测试的。**"

他给的机制：**网络安全的奖励函数定义得极其清晰**——"拿到数据的访问权。它拿到了吗？给奖励。"因此这是**RL 问题空间的黄金候选**：

> "**构造一个挑战根本不难。**就算不存在已知漏洞——如果我们说的是零日——**你就在模型和某份数据之间放一个软件，然后说'拿到这份数据'。它拿到了，你就给奖励。就这么简单。**"

- 关于数据来源，主持人插话"因为它们过去四年一直在买渗透测试数据，对吧？"、"还有 CTF 比赛那类东西"，Dylan 的回应是"**那是其中一块**"——但他强调真正关键的是上面那个**可自动构造的挑战**，而不是买来的数据。

### 然后是本节的核心：奖励"最少 token"改变了什么

> "**但它们在上面又叠了一层，这才是真正开始变得有意思的地方：它们开始奖励 token 数最少的路径。**"
> "**这之所以有意思，是因为这是第一次能够可量化地向我们展示，从 A 到 B 的一般性网络安全最省力路径到底是什么。**"

- 他明确承认自家的偏见并把它当成待验证的假设：**"Truffle Security 带偏见的看法当然是：一个躺在那儿的密码，比走一个花哨的零日路径要短。"**
- **但真正的转变是从观点变成观测**："**真的看着模型从物理上从 A 走到 B，看着它跟着那个密码走，并且量化走这条路花了多少 token、走那条路又花了多少**——这实在是很惊人。"

⚠️ **本库标注**：这条对本库有两处接口——
1. 对 [评估与 Benchmark](https://github.com/nolimitkun/ai-kol-wiki/blob/main/topics/evaluation-and-benchmarks.md)：这是一个**副产品性质的度量**（为了省成本而设的奖励项，意外产出了攻击路径的经验排序），本库此前没有这一类。
2. 对 [LLM 训练管线](https://github.com/nolimitkun/ai-kol-wiki/blob/main/topics/llm-training-pipeline.md)：**token 效率奖励会改变模型选择的策略类型，而不只是改变长度**——这一点在本库既有的 RL 讨论里没被记录过。

**主持人的一句归纳**（[00:11:04]）："**这完全合乎逻辑啊。拿到一加仑牛奶最快的方式就是偷一加仑牛奶。**"

## 三、供应链为什么成了最低垂的果实

- **模型和人类黑客走同一条路**（[00:03:02]，Fas）："就像人一样，模型会挑进公司最容易的那条路，**而现在最低垂的果实变成了往公共注册表发布恶意软件，因为它们知道那里没有任何审核在发生，而开发者很可能就装了**。"
- ⚠️ **"通用幻觉包名"**（[00:04:02]，Fas）：他提到最近有研究把这个现象叫作**"universal typosquats / universal hallucinations"**——**所有前沿模型都犯同一个错误，都假定某些其实不存在的包是存在的，尽管这些模型来自不同公司**。**转录稿未给论文名或作者，本库未核实。**
- **AI 同时也是入口**（[00:04:02]，Fas）：非开发者也在用这些工具无意中写代码、拉包（做图表、做可视化），"**没人真的知道装进来的是什么、在发生什么**"。他的定性很朴素——"这听起来像科幻，**但其实就是最基础的东西：我们在用什么软件？我们怎么审它？**"
- **Dylan 从凭证侧接上同一条逻辑**（[00:05:02]）：站在模型的位置上，目标是拿到数据，**给 Apache 装后门是很有效的方式**；那么"你是用这个直接就能登录的密钥，还是烧掉一堆又一堆 token 去找一个零日？"——**"它们被优化成用最少 token 达成目标，当然会用那个大喇喇躺在外面的密钥。"**

## 四、当天正在发生的 npm 蠕虫：机制被讲清楚了

**这是本期证据等级最高的部分——录制时事故正在进行中**（[00:12:06]–[00:15:08]）。

- **规模**：不是一个仓库，是"**几百个**"（[00:12:06]）。
- **蠕虫这个概念的历史**（Fas）："**很长时间以来人们一直在谈 npm 蠕虫这个概念**"——给某个包装后门 → 开发者安装 → 用安装时窃取的访问权自我传播 → 很快接管 npm。"**这在博客文章里被传了很多年，直到有人真的想到去做。**"
  - 关于是不是 AI 干的：主持人问"多半是用 AI 做的吧？"，Fas 答 **"几乎可以肯定，是的"**，并给了两条佐证：① "**我们有相当好的理由相信那个恶意软件是 vibe coded 的**"；② **有一个威胁团伙把自己 vibe coded 的工具包开源了出来给别人用**，此后已出现模仿攻击。
  - ⚠️ **一句很好的启发式**（[00:14:08]，主持人）："**恶意软件作者向来不是什么好程序员。所以如果代码开始变好看了，那多半是 vibe coded 的**——这跟大家通常对 vibe coding 的印象正好相反。"

### ⚠️ 本节最该被记的两条机制

**① 归因：不是端点被黑，是 CI 配置泄了 token**（[00:14:08]–[00:15:08]，Fas）

他们当天早上跟那位 maintainer 通了电话，对方"**老实说还没搞清楚发生了什么**"。Fas 的**初步、明确标为推测**的判断是：

> "可能是一个不安全的 **GitHub Action**，攻击者能借它最终让自己的代码跑起来，然后**从环境变量里把 token 拿走**。我们还在确认，但看起来是这样。而**这类蠕虫我们已经见过很多次了**。"
> "**所以他的端点很可能其实是好的，根本不是问题的一部分。问题就是那个不安全的 GitHub Action。**"

⚠️ 本库标注为**事发当天的初步归因，Fas 自己两次标注"仍在确认""这是推测"**。

**② payload 本身就是 prompt——绕过 EDR 的新手法**（[00:14:08]，Fas）

> "有意思的是它们经常**利用开发者机器上已经装好的 AI 工具**去走得更远、去绕过一些传统安全工具。我们看到**本地 CLI 工具基本上被拉进攻击链里，被当成跳板**。所以**很多时候 payload 其实就是 prompt**。而这**绕过了很多典型的 EDR 工具**——因为那只是一个 markdown 文件，你的 Claude 在跑它，里面可能就是让它翻遍系统、找出所有密钥和看起来值钱的东西。"

主持人补的一句：**"你的 EDR 工具肯定不认识这个 JSON blob 和一个 .md 文件。"**
Fas 的加码：**"而且开发者机器本来就一直在做各种奇怪的事——你在给 Claude 提示、它在你文件系统上到处折腾，所以什么都不太像是异常。"**

⚠️ **本库标注**：这是本页 [提示注入](https://github.com/nolimitkun/ai-kol-wiki/blob/main/topics/llm-security.md#攻击类型karpathy-2023-11-的分类) 那条线**第一次落到具体的商业攻击载荷形态**上。它同时对 [Gray Swan 的 lethal trifecta](https://github.com/nolimitkun/ai-kol-wiki/blob/main/topics/llm-security.md#agent--computer-use-时代的攻击面gray-swankolter--fredrikson2026-06) 补了一个此前没有的性质：**在开发者机器上，"异常检测"这条防线在结构上失效了，因为 agent 的正常行为与攻击行为在遥测上不可区分。**

| 事项 | 数字 | 出处 |

## 六、行业的三条应对，以及每条的代价

### ① npm 的强制交互式 2FA（有明确日期，可跟踪）

（[00:16:09]–[00:17:09]，Fas）

- **事实**：npm 已宣布计划**在 2027 年 1 月**要求**任何新发布之前必须有人工交互式 2FA 确认**。
- **判断**："**那大概会彻底杀死整个蠕虫这个概念。**"
- ⚠️ **但代价被明说了**："**会极度具有破坏性，因为所有人都把这套接到自动化上了**——GitHub Actions 触发发布。所以他们做这件事的时候基本上会**把整个生态搞坏**。**但我认为这是对的决定。**"
- **覆盖不到的部分**："还有其它**由志愿者运行、没有 GitHub 和微软背书**的生态，**它们大概不会做这些改动**，所以我认为我们还会继续看到这类事。"

### ② 更快打补丁——以及为什么现在做不到

（[00:07:04]–[00:08:04]，Fas）

- **诊断**："**前沿模型正在造成漏洞发现与漏洞利用之间时间差的大幅压缩。**"（早上公布漏洞，下午就有利用可用）
- **瓶颈不是意愿是工作量**："我们不能要求安全团队和开发者去做那种繁重的打补丁流程——**从团队在用的某个古早版本一路升级跨越多个大版本，那工作量太大了，可能还要重构应用代码。**"
- **最难的一块**："还有**大量遗留应用基本处在维护模式、无人维护、或者在我们合作的很多公司里压根没有工程师被指派**去管它们。"
- **结论是一个尚未存在的东西**："**我们作为一个行业得想出新办法来快速打这些补丁。**"（⚠️ 他没有给方案，只给了问题定义）

### ③ 出钱——本库第一条给出数量级的注册表资助建议

（[00:19:09]–[00:20:09]）

- **Dylan 提的问题很具体**：他们在 **Ruby Gems** 里发现过一个**缓存问题，可以窃取任意 token、拿到任意账号、给任意包装后门**；对方"很好合作，很快修了"，但那是一个**资源不足**的组织。他由此问：一家公司在选技术栈时，**该不该把"这个包管理器背后有没有安全团队"算进决策**？
- **Fas 的回答分两半**：
  - 换语言不现实——"**很难让人因为这个就整个换语言，如果他们已经建在上面了。**"
  - **可操作的那一半**："**最可行的事情是大家应该出钱资助这些东西。要多雇一两三四五个安全人员，在这些基金会里其实花不了多少钱，但能带来非常大的差别。**"
  - ⚠️ **本库最该记的量级**："**不需要很多家公司各开 2.5 万、5 万美元的支票，就能给这些人带来很大差别。**"
  - 主持人补了一句：**"或者给他们多点推理算力去跑测试、去打补丁。"**
- **Fas 对责任分配的立场**（[00:17:09]–[00:19:09]）：顶级 maintainer"**没有安全团队，没有企业 SLA，他们是志愿者，只是把代码放在 GitHub 上**"。因此——
  > "**所以我认为责任其实落在使用者身上，要去审自己在用什么。很难说'我们是家公司，我们在网上找到这段代码，直接部署到生产环境了，这是别人的错'。不是的，**这些软件的用户对自己引进环境的东西确实负有一部分责任。"
  > 但他立刻自我限定：**"我不想把太多责任推到人身上，因为这是个难题。"**
- **一个很人性的例证**（[00:17:09]）：他多年前看到一位高产的 npm maintainer 输密码，"**我没看到密码，但我看到它太短了**……我就问他，你的密码怎么是六个字母？"对方住在丹麦，"**一个高信任社会**"，观点是"我不想活在恐惧里、老想着这些事"。

## 七、收尾：两个人各自的"本周最大观察"

**主持人的提问**（[00:20:09]）：你们不是来见我们的，我们都是为 Black Hat 来的——**今年的气氛怎么样？**

- **Fas：**"**2026 年是软件供应链之年。**"（[00:20:09]–[00:22:10]）
  - 变化不在攻击本身而在**认知**："**往年我总得去教育人们**……有时会得到'哦是啊，但真的有多大可能'这种反应，我们就说'不，可能性非常高，我给你讲讲会怎么发生'。"
  - "**而今年它真的突破进了主流**，有主流出版物、商业媒体在报道这些攻击"（主持人插话："在 Bloomberg 上是头条了"）。
  - ⚠️ **他的结论是反直觉的乐观**："**你需要那种空中掩护，安全团队才能真的把这些问题排上优先级、才能找到预算。**所以尽管这些攻击现在处理起来很痛苦，**我认为最后我们会从这里出来变得非常强，因为我们真的会拿到预算**。"主持人的归纳是"**这肯定是一次免疫接种**"。
  - 一个小观察："**我注意到攻击者似乎专挑 RSA 和 Black Hat 的时候开始这些 npm 蠕虫。**"（因为安全人员都不在办公室）
- **Dylan：秘密管理的"旧卫队"正在被换掉**（[00:22:10]–[00:23:10]）
  - 事实侧：**HashiCorp 被收购、CyberArk 被收购**，"老一代被挤出去了"。
  - 他认为这打开了一场**关于非人身份（non-human identity）与秘密的新对话**：怎么让它们更好用、怎么把它们吊销掉、"**怎么真的推动行业往前走，这是我们在旧卫队之下做不到的**"。
  - 他把与 HuggingFace 这类平台的合作定性为**杠杆点**："所有从各处抓来的数据**创造了一个中心位置，我们可以在那里扫描并取得实质进展**。"

### ⚠️ 全篇最后一句，也是最该被后续跟踪的一句

主持人抛的结构（[00:23:10]）：**"我能想象会有一个乘数效应：过去是一个用户十个密码，现在会是十个 agent 十个密码。"**

Dylan 的回答，是本页唯一一句没有任何限定词的判断：

> **"agent 现在与秘密交互的方式是一个蛮荒西部式的、尚未解决的问题，我们正在非常努力地解决它。"**

⚠️ **本库标注**：这与本库 [NanoClaw 的隔离模型](https://github.com/nolimitkun/ai-kol-wiki/blob/main/topics/llm-security.md#个人-agent-的隔离安全模型gavriel-cohen--nanoclaw2026-06)（**agent 环境里不放任何凭证**，出站经 vault 代理注入）是**同一问题的解与题**——NanoClaw 给的正是"agent 与秘密如何交互"的一个架构答案。**值得注意的是 Dylan 作为凭证侧的专业厂商，把这件事描述成"未解决"**，而 NanoClaw 是个人 agent 的单点方案。两者不矛盾：**架构上可解，生态上未解。**
